## 实现与判断依据

本次阅读现有 VFS、清单解析器及历史提取证据。当前清单提供哈希和 Bundle 依赖，不能仅靠清单列出角色名称；因此采用“VFS 元数据 + 可见名称候选 + 清单依赖”的发现流程。并未把明文名称认作已经解析出的 Unity 对象。

1. 核对本机 GameAssembly SHA256，仅支持既有 `20260821_c24495e5` 版本配置。
2. 枚举同名 BLC 的有效 VFS 分组，经原生辅助程序解密，由现有严格 v4 解析器读取文件记录。
3. 从 VFS 定位唯一 `manifest.hgmmap`，只提取清单到工作区；检查解密后 MD5，解压 Brotli，严格解析清单 Bundle 表和依赖引用。
4. 以 4 MiB 分块读取相关 CHK，保留重叠字节，查找 `chr_<数字>_<代码>_uimodel/model` 和 `A_actor_<代码>_...` 名称。
5. 将命中位置映射回其 VFS 文件记录，排除加密记录及超出 Bundle 边界的命中。保留名称、所属 Bundle、CHK 及偏移证据。
6. 根据完整的 `initial/...`／`main/...` 清单路径匹配 VFS，展开直接依赖图；处理循环，保留缺失／歧义信息，不只靠 basename 匹配。
7. 生成角色代码候选、资源列表、索引报告。报告状态是 `discovered`；`decoded`、`adapted`、`verified` 均为 false。

脚本只读游戏；新建文件位于用户独立工作区。没有调用模型、动画导出器或 Unity。Brotli 解压只接受正确的清单魔数，并设 512 MB 输出上限。

## 缓存、取消与日志

- 每个已完整扫描的 CHK 作为一次 SQLite 事务提交，保存命中和扫描时 SHA256。
- 复用依据：游戏摘要、扫描器版本、该分组 BLC 的 SHA256、CHK 长度与修改时间。复用时不重新计算整个 CHK 摘要；内容被人为改写但长度与时间均保留可能无法识别，勾选“重新扫描”可绕过复用。
- 扫描结束再次核对 BLC 和 GameAssembly，发生更新时不发布本次结果。缺失的 CHK 和跳过的加密记录写入报告与覆盖说明。
- 同工作区使用进程持有的文件锁，避免两个扫描任务同时改缓存。
- 取消会停止扫描进程及其子进程，不使用旧索引冒充本次成功。下次重新读取分组与清单，复用已完整提交的 CHK；当前中断文件重新扫描。
- 日志保存在工作区 `index/logs`，缓存和最近完成索引在 `index/<游戏摘要前16位>/plaintext-candidates-v1`。结果事件与成功退出都具备时，界面才导入本次索引。

## 界面与计划变化

- “扫描游戏资源”“取消扫描”“重新扫描”及“扫描记录”页。
- 角色搜索之外新增资源名称／路径筛选；隐藏条目的勾选保留，计划显示实际选中数量。
- 扫描候选默认不选中，显示关联依据和覆盖范围。没有中文名称表的角色只显示代码，不猜译名。
- 候选可保存为待确认计划，包含用户勾选的模型候选及清单依赖图；不会把同代码的所有模型猜作动画依赖，没有自动生成 Avatar、RootPathID 或播放模式。
- 新增“角色与骨架确认”阶段，尚无通用提取执行器，不能执行这些计划。
- 配置导入及旧的陈千语窗口保留；旧 JSON 缺少新增字段时使用默认值。

## 当前限制及下一步

名称扫描不是穷举：压缩或加密数据、其他命名规则、非 ASCII 字符串、共享动画归属都可能漏项。明文名称也可能是引用或路径，不能证明对应 Bundle 含有同名 AnimationClip 或完整模型。

后续需要解析候选的实际对象及容器路径，确定精确根节点、PathID、Avatar、模型范围和动画类型；再接入选择性提取、适配及真实阶段结果。执行前仍需检查依赖文件可用性和摘要，不能因为元数据依赖完整就假设下载文件齐全。

本次仅做代码实现、C# 构建和 Python 语法编译，尚未运行扫描器或交互测试；未生成本机角色数量或性能的实测结论。当前验证过的六条待机和两条行走属于此前交付，不能代替本模块验证。
